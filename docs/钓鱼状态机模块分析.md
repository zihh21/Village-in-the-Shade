# 玩家钓鱼状态机模块分析（CState_Player_FishingRod）

> 本文档记录《Village in the Shade》玩家主状态机中"钓鱼"子状态机的反编译分析结果，
> 是 FishingAutoCatch v1.0.0 新增 Hook 点 C（续竿）/ Hook 点 D（入包/背包满）的定位依据。
> 工具链与切片产物见 `docs/反编译代码索引文档.md`（总索引）。
> 所有地址均为 rva（ImageBase `0x140000000`）。

## 1. 概述

玩家对象（r14/rdi 寄存器持有，随调用不同可能落在别名寄存器）内嵌一段"钓鱼"子状态机，
按 `[player+0x1D8]`（主状态）经跳转表 `0x216F48` 分发到 8 个 handler（state0..state7）。
`[player+0x1DC]` 为"目标状态"——各 handler 通过写该字段推进状态机（下一帧生效）。

该状态机负责完整的钓鱼流程：甩竿 → 等咬钩 → 咬钩结算（入包）→ 收竿动画 → 续竿/停止。

### 玩家对象关键偏移

| 偏移 | 类型 | 说明 |
|---|---|---|
| `+0x1D8` | dword | 主状态（跳转表索引，0..7） |
| `+0x1DC` | dword | 目标状态（写入后下一帧生效；state1 写 7=手动收杆，state2 超时写 5，state5 续竿点写 1，Hook C 自动模式写 0） |
| `+0x1E0` | struct | 时间轴/动画等待对象（各 handler 开头 `lea rcx,[r14+0x1e0]; call 0x666f50` 查询"动画播完"） |
| `+0x1F4` | float | 甩竿力度（钳位到 [0.1,1]，state3 段写入） |
| `+0x208/+0x20C` | dword | 子状态（1=准备、2=活动中，v0.3.x 分析） |
| `+0x238` | qword | 任务指针（CTask_Menu_Fishing，Hook C resume 处 `cmp [r14+0x238],rbx` 判空） |
| `+0x240` | qword | 输入对象（按键查询经此；0x497=收杆键、0x498=收线/咬钩确认、0x55a=命中小游戏键） |
| `+0x290/+0x2A0` | qword | 浮标对象（state5/state6/state7 多处 `mov rcx,[r14+0x290]; call 0x17a8f0` 取浮标状态） |
| `+0x2A8` | float×2 | 浮标位置（Hook C 复放 `movsd [r14+0x2A8],xmm0` 写入） |
| `+0x2C8` | qword | 场景对象 |
| `+0x2D0` | float | 收竿耗时（state6 计算并传给 0x791d20 记录） |

## 2. 状态分发跳转表（0x216F48）

跳转表为 **8 项 dword 数组**（位于 `.text` 段对齐填充区之后，直接按 qword 读取会误判为
`0x0021567C002153E3` 这类拼接值，实际是两个小端 dword）：

| 索引 | handler rva | 状态语义 |
|---|---|---|
| 0 | `0x2153E3` | **state0**：甩竿状态（Hook C 自动模式写 0 回到此处实现重甩；标准"时间轴等待帧"结构） |
| 1 | `0x21567C` | **state1**：等待/咬钩（0x215743 检测收杆键 0x497 → 写 7 手动收杆；等咬钩后创建节奏任务） |
| 2 | `0x215AAE` | **state2**：等咬钩超时（超时 → 写 5 进收竿动画；路径汇入 Hook C） |
| 3 | `0x215E28` | **state3**：过渡帧（无 0x666f50 等待调用，推测为短暂过渡，未深入） |
| 4 | `0x2160CE` | **state4**：咬钩结算（读 `[rax+0x568]` 子状态；两路汇合到 0x216B46 入包调用点 = **Hook D**） |
| 5 | `0x216BFB` | **state5**：收竿动画（0x216C7F 调 0x7491b0 判动画播完 → 0x216C9C 续竿点 = **Hook C**） |
| 6 | `0x216CD0` | **state6**：收竿后处理帧（结构类似 state1 等待帧，推测为动画后收尾等待，未深入） |
| 7 | `0x216DA9` | **state7**：收竿后收尾（发消息 0xAA、取 "fish" overlay 0x749f80 等，推测为结算展示，未深入） |

状态推进全部通过写 `[player+0x1DC]` 目标状态完成；本 Mod 只改写该字段的**目标值**，
不破坏原有推进机制。

## 3. 关键路径与证据

### 3.1 正常收杆循环（原版）

```
state1（0x21567C）
  ├─ 0x215743  检测收杆键 0x497 → [player+0x1DC] = 7   ← 手动收杆（玩家停止入口）
  └─ 咬钩 → 创建 CTask_Menu_Fishing（0x215882 持有方式，rva 0x38A860 update）
state4（0x2160CE）
  ├─ 0x2160E6  mov edi,[rax+0x568]（结算子状态存 [rsp+0x38]）
  ├─ 0x216A73  jmp 0x216B46              ← 路径 A 直接进 Hook D
  ├─ 0x216A78-0x216B41  结算/合成段（call 0x18bdb0 后顺序落入 0x216B46）← 路径 B
  └─ 0x216B46  入包调用点（Hook D，45 字节，resume 0x216B73）
state5（0x216BFB）
  ├─ 0x216C05  call 0x666f50             ← 时间轴等待查询
  ├─ 0x216C7F  call 0x7491b0; test al; je 0x216f04 ← 动画播完才继续
  └─ 0x216C9C  续竿点（Hook C，26 字节，resume 0x216CB6）
        原版写 [player+0x1DC] = 1 → 回 state1 等待
```

### 3.2 Hook C：续竿 / 自动重甩（rva 0x216C9C，26 字节）

原始覆盖段（`scripts/dump_hook_bytes.py` 从 village.exe 按 RVA dump 确认）：

```asm
0x216C9C: F2 0F 10 44 24 50              movsd  xmm0, [rsp+0x50]      ; 6B
0x216CA2: F2 41 0F 11 86 A8 02 00 00     movsd  [r14+0x2A8], xmm0     ; 9B（REX.B 0x41 在前缀组最后）
0x216CAB: 41 C7 86 DC 01 00 00 01 00 00 00  mov dword [r14+0x1DC], 1 ; 11B
0x216CB6: 49 8B 5E 38                    mov rbx, [r14+0x38]           ← resume（下一条指令）
```

合计 6+9+11 = **26 字节**（早期笔记记 24B 有误，已修正）。
`0x216C9C`/`0x216CAB` 无任何 call/jmp 进入（`callxref`/`jmp` 扫描确认），可安全整段替换。

stub 行为：复放两条 movsd → 检查 `gEnabled`/`gBagFull` →
- F8 关（gEnabled=0）或背包满（gBagFull=1）→ 写 1（原版行为，停止自动循环）；
- 自动模式 → 写 **0** 回 state0 重新甩竿（刷新浮标位置，实现自动循环）。

**超时重甩无需单独 hook**：state2 等咬钩超时 → 写 5 → state5 收竿动画 → 同样汇入
0x216C9C 续竿点，被 Hook C 统一改写。原候选点 0x215E0A 只有 10 字节不足 detour，
且 `0x215DF7 je 0x215E0A` 直接跳入其内部，不可前扩——Hook C 方案同时规避了这两个问题。

**停止路径**：玩家在 state1 按收杆键 0x497 → 原版 0x215743 写 7 → 手动收杆流程。
Hook C 不拦截该路径（自动模式下每次续竿都回 state0，state1 只在咬钩瞬间短暂存在，
0x497 检测仍生效），因此"按游戏内收杆键立即停止"天然成立。

### 3.3 Hook D：入包 / 背包满检测（rva 0x216B46，45 字节）

原始覆盖段（同上 dump 确认）：

```asm
0x216B46: 48 8B 05 83 8F EC FF           mov rax,  [rip+0xEC8F83]      ; → 0x10DFAD0 全局单例
0x216B4D: 48 8B 88 08 02 00 00           mov rcx,  [rax+0x208]         ; 持有物容器
0x216B54: C6 44 24 20 01                 mov byte [rsp+0x20], 1
0x216B59: 45 33 C9                       xor r9d,  r9d                 ; 原编码（非 4D 33 C9）
0x216B5C: BA 1A 04 00 00                 mov edx,  0x41A               ; 物品类别 id
0x216B61: 41 B8 06 00 00 00              mov r8d,  6                   ; 数量/品质参数
0x216B67: 48 8B 89 B8 32 00 00           mov rcx,  [rcx+0x32B8]        ; 背包容器
0x216B6E: E8 4D 20 F2 FF                 call 0x138BC0                 ; 持有物添加 + 容量判定
0x216B73: 49 8B 45 00                    mov rax,  [r13+0]             ← resume（下一条指令）
```

`0x216B46` 全段无 call/jmp 进入，可安全覆盖；`0x216A73` 的 `jmp 0x216B46` 会一并跳入 stub。

stub 行为：复放全局取值与参数装载（`movabs r11, base+0x10DFAD0` 替代 rip 相对寻址）→
`movabs r11, base+0x138BC0; call r11` 复放原始调用 → 检查返回值 al：

- `al==0`（0x138BC0 满路径返回）且 gEnabled=1 → **gBagFull=1**（Hook C 停续竿 + 加载器提示）；
- `al==1`（成功）且 gEnabled=1 → **gFishCount++** 且 gBagFull=0（清包后自动恢复自动循环）。

只用易失寄存器（rax/r11/rcx/rdx/r8/r9），r13 必须保留（resume 处 `mov rax,[r13]` 依赖）。

### 3.4 持有物添加 0x138BC0（容量判定）

- 入口：`0x138BC0`（foff `0x137FC0`，函数长 0x298+ 字节）。
  参数：rcx=背包容器（来自 `[持有物容器+0x32B8]`）、rdx=0x41A 类别、r8d=6、r9b=标志、`[rsp+0x20]=1`。
- **满路径**（`0x138DF5`-`0x138E13`，`out_138bc0_tail*.txt`）：
  容量 clamp 后发送消息 **0x3EB**（"背包已满"UI 提示，`call 0x748d50` 投递到全局单例）
  并 `xor eax,eax` 返回 **0**。
- **成功路径**（`0x138ED3` → `0x1390C2`）：正常插入后 `mov al,1` 返回 **1**。

因此"检测背包是否已满"的最可靠办法就是**观察本次添加调用的返回值**——
不依赖 UI 消息解析，也不需要硬编码容量上限，天然适配任意容量修改。

### 3.5 全局单例 0x10DFAD0

`.data` 中的全局单例（`mov rax,[rip+0xEC8F83]` 目标）：
- `[+0x208]`：持有物容器对象；
- `[+0x208 + 0x32B8]`：背包容器（0x138BC0 的 rcx 来源）。

同款取值序列在 `0x216EA8`（state7 内，`mov r8d,3` 不同参数）亦出现一次，
证明这是"向持有物容器添加条目"的通用样板，Hook D 复用其精确字节保证行为等价。

### 3.6 输入查询 0x7EF810 / 0x7EF970

- `0x7EF810`：rcx=输入对象、edx=键 ID、r8=结果结构；返回 al=1 激活/按下。
- `0x7EF970`：键值表遍历子例程。
- 关键键位：`0x497`=收杆键、`0x498`=收线/咬钩确认、`0x55a`=命中小游戏键。

**Hook C 不查 0x497**（v1.0.0 最终决策）：stub 内调 0x7EF810 需预先构造输入描述结构
（0x2156EA-0x21573B 含 0xE587C0/0xA13B06 指针）并伴随 `inc [输入实例+0xBC]` 副作用，
且 state1 原版 0x215743 已能捕获收杆键——故查询逻辑从 stub 中删除，停止依赖原版路径。

## 4. 与 Mod 的对应关系

| Hook | rva | 长度 | resume | 作用 |
|---|---|---|---|---|
| A | 0x38A860 | 15 | 0x38A86F | 节奏小游戏音符全命中（详见 `钓鱼节奏小游戏分析.md`） |
| B | 0x38B2FD | 6 | — | 成功检查 je→NOP（同上） |
| **C** | **0x216C9C** | **26** | **0x216CB6** | 续竿点：自动模式写 0 重甩 / 停止写 1 走原版 |
| **D** | **0x216B46** | **45** | **0x216B73** | 入包调用复放：按 al 维护 gBagFull / gFishCount |

stub 代码见 `src/FishingAutoCatch/HookStub.cs`（布局与 Hook A）与
`src/FishingAutoCatch/CastHookStub.cs`（Hook C/D）；
结构校验脚本 `scripts/verify_stub_v100.py`、原始字节 dump `scripts/dump_hook_bytes.py`。

## 5. 未解决问题 / 后续可深入

- state3（0x215E28）确切语义未确认（无时间轴等待调用，疑似短暂过渡帧）。
- state6/state7 的收尾细节（消息 0xAA 含义、"fish" overlay 展示时机）仅作初步观察。
- `[player+0x1F4]` 甩竿力度的来源（是否与蓄力条 UI 相关）未分析。
- 0x138BC0 内部完整容量比较逻辑（clamp 边界、各类别独立容量）未逐行展开，
  仅确认返回值语义（0=满、1=成功）与消息 0x3EB。
